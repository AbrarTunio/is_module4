Lesson 1 of 3

One-way hash functions: MD5, SHA and RIPEMD

What a hash is, the five properties it must have, why the birthday paradox halves security, and which algorithms are still safe.

Step 1

The hash machine

Put in a word, a sentence or a whole book. The output is always the same size. SHA-256 always gives 256 bits, shown as 64 hex characters.

Input length: bytes
⚙️SHA-256
Output length: 32 bytes, every time
Hashing is not encryption. There is no key, no decryption and no way back. "The password is encrypted with SHA-256" is wrong twice: SHA-256 is not encryption, and there is nothing to decrypt.

👀 What you should see

Whatever you type, from one letter to a full paragraph, the output is always 64 hex characters (32 bytes). The input bar grows; the output bar never changes. The reverse button fails.

💡 Takeaway

A hash is a fixed-size, one-way fingerprint of data. It has no key and no decryption, so hashing is not encryption.

Step 2

The five properties

A good cryptographic hash must have all five. Click each one to see it in action.

👀 What you should see

Different-sized inputs give same-sized digests, "hello" always gives the same digest, thousands of hashes finish in milliseconds, and changing one letter changes everything.

💡 Takeaway

A cryptographic hash needs all five properties. When one is lost, especially collision resistance (as with MD5 and SHA-1), the algorithm is broken for security use.

Step 3

Avalanche effect: one letter, half the bits

Change one character. About half of the 256 output bits flip. Red squares are bits that changed.

Why it matters: if similar inputs gave similar digests, an attacker could learn about the message by looking at the digest. Avalanche means the digest leaks nothing about how close two inputs are.

👀 What you should see

Changing a single character flips about 128 of the 256 bits, around 50%, scattered with no pattern.

💡 Takeaway

Similar messages give completely unrelated digests. A digest reveals nothing about the message, or about how close two messages are.

Step 4

Three kinds of attack, three resistances

Analogy: secret PINs in a big city. Imagine every person in a city picks a secret 4-digit PIN. There are only 10,000 possible PINs (0000 to 9999). Think of each person as a message and their PIN as its digest. A hash works the same way: endless possible messages, but a limited number of digests, so some messages must share one. The question is how hard it is to find them.

Preimage

Given: a digest.
Find: any message that produces it.

🔢 You see the PIN 4721. Find anyone whose PIN is 4721. You must ask about 10,000 people.

Cost for an n-bit hash: 2n

Second preimage

Given: a message.
Find: a different message with the same digest.

🔢 Here is Ali. Find someone else with Ali's PIN. The target is still one fixed PIN, so again about 10,000 people.

Cost: 2n

Collision

Given: nothing.
Find: any two messages with the same digest.

🔢 Find any two people who share any PIN. Every new person is compared with everyone already asked, so only about 100 people (√10,000). The birthday effect again.

Cost: only 2n/2

What does "cost" mean?

Cost = how many guesses the attacker must try, on average, before succeeding. One guess means hashing one message and checking the result. A good hash has no shortcut, so guessing is all the attacker can do. It is like trying keys on a lock one by one: cost is the number of keys, and attack time = cost ÷ guesses per second.

Step 5

The birthday paradox

How many people must enter a room before two probably share a birthday? Most people guess about 180. The answer is 23, because we count pairs of people, not people. 23 people make 253 pairs.

People in room: 0   Pairs: 0  

Chance of a shared birthday with 23 people:

Same idea for hashes: to find a collision in an n-bit hash you need about 2n/2 tries. So against collisions, the security you really have is half the output bits. Nothing is lost; that is simply the true level.
HashOutput bitsPreimage securityCollision security
MD51282128264, and broken far below that
SHA-11602160280, broken in practice
SHA-25625622562128
SHA-51251225122256

👀 What you should see

The room usually gets a shared birthday at around 20 to 30 people. The slider shows the chance passes 50% at just 23 people.

💡 Takeaway

Matches appear quickly because we count pairs, not people. So the output size is not the security level: SHA-256 has 256 output bits, but the security you really have against collisions is 128 bits (against preimages it stays 256). 128 bits is still far beyond any attacker. Rule: for k bits of collision security, choose a hash with 2k output bits.

Step 6

The algorithms and their status

Dark bar: output size. Violet bar: real collision security (half). Type below to see three of them hash the same text.

Real damage: in 2012 the Flame malware used an MD5 collision to fake a Microsoft certificate and spread through Windows Update. In 2017 Google's SHAttered attack made two different PDFs with the same SHA-1 hash. If you see MD5 or SHA-1 used for signatures, certificates or integrity checks, report it.

👀 What you should see

The same input gives digests of different lengths for each algorithm. MD5 and SHA-1 are marked broken; SHA-2, SHA-3 and BLAKE are secure.

💡 Takeaway

Use SHA-2, SHA-3 or BLAKE2/3. MD5 or SHA-1 used for signatures, certificates or integrity checks is a security finding. MD5 is acceptable only as a non-security checksum.

Step 7

Length extension: continuing someone else's hash

MD5, SHA-1 and SHA-2 process the message block by block, passing a running "state" along. The final state is the digest. So an attacker who sees the digest can pick up where it stopped and keep going.

secret + message→ block 1→state→ block 2 + padding→final state = H(M)
😈Attacker copies H(M) as the starting state→ "&amount=99999"→new valid tag

ConstructionVulnerable to length extension?
MD5, SHA-1, SHA-256, SHA-512Yes
SHA-512/256 (truncated)No output is shorter than the state
SHA-3, BLAKE2No different design
HMAC over any of themNo by design (Lesson 2)

👀 What you should see

The attacker takes the published tag, continues hashing their own extra data, and gets a valid tag without ever knowing the secret.

💡 Takeaway

Never build a MAC as H(secret ‖ message) with MD5, SHA-1 or SHA-2. Use HMAC (or SHA-3 / BLAKE2).

Message authentication: MACs and HMAC

Encryption hides a message. Authentication proves it is genuine and unchanged. These are different jobs.

Step 1

Alice, Bob and Mallory in the middle

Mallory cannot necessarily read messages, but she can change, delete or replace them. Bob needs to answer two questions: was it changed? (integrity) and did it really come from Alice? (origin).

Key lesson: a bare hash sent next to a message authenticates nothing. Anyone who changes the message can just recompute the hash. You need something the attacker does not have: a secret key.

👀 What you should see

With a plain hash, Mallory's change is accepted and Bob is fooled. With HMAC, the same change is rejected. With tampering turned off, both modes accept the genuine message.

💡 Takeaway

Integrity against attackers needs a secret. A bare hash catches accidents, not attackers. A MAC proves the message is unchanged and came from someone holding the key.

Step 2

Three approaches to authentication

(a) Encryption

Encrypt everything. If it decrypts to something meaningful, it came from a key-holder.

Weak: random data always "decrypts" to something, so Bob cannot tell.

(b) MAC

Send the message in the clear, plus a tag made from the message and a shared key: T = MAC(K, M)

Message stays readable, but cannot be forged.

(c) Hash

Hash the message and protect the digest: encrypt it, sign it, or mix in a secret.

Mixing in a secret is a MAC again.

Authentication without encryption is often exactly right: a public alert that must not be faked, a packet header a router must read, or a stream you want to check before decrypting.

👀 What you should see

Encryption-only authentication fails on random data, a MAC authenticates while leaving the message readable, and a hash only helps if the digest is protected.

💡 Takeaway

Authentication and confidentiality are separate goals; you can have either one without the other. A MAC is the standard way to authenticate without hiding.

Step 3

Inside HMAC, step by step

The naive H(key ‖ message) falls to length extension. HMAC fixes it by hashing twice, with two different versions of the key. These are real values computed in your browser.

HMAC(K,M) = H( (K ⊕ opad) ‖ H( (K ⊕ ipad) ‖ M ) )

PartWhy it's there
Two nested hashesThe outer hash hides the inner state, so length extension fails
ipad (0x36) and opad (0x5C)Turn one key into two different keys
XOR with the keyCheap, and takes the same time for every input
Key padded to block sizeLets you use a key of any length
Always compare tags in constant time: hash_equals() in PHP, hmac.compare_digest() in Python. A normal comparison stops at the first wrong byte, and that timing leaks the tag.

Other MACs you will meet: CMAC (built from AES), GMAC (the authentication half of AES-GCM), Poly1305 (used with ChaCha20 in TLS 1.3).

👀 What you should see

Five steps produce the tag. Change one letter of the key or the message and every later step, including the final tag, changes completely.

💡 Takeaway

HMAC hashes twice with two keys derived from one, so the outer hash hides the inner state and length extension fails. Use HMAC-SHA256 and compare tags in constant time.

Step 4

A MAC proves one of us wrote it. A signature proves you wrote it. Use a MAC between parties that trust each other (your own services, a session). Use a signature when a third party must be convinced: contracts, software releases, certificates.

👀 What you should see

The judge cannot decide who wrote a MAC-protected message, but can name Alice when the message carries her signature.

💡 Takeaway

A MAC proves one of us wrote it; a signature proves you wrote it. If a third party must be convinced or the sender must not be able to deny it, use a signature.

Lesson 3 of 3

Applying hashes: passwords and integrity

Why fast hashes are wrong for passwords, what salt and work factor do, and how to verify a download properly.

Step 1

Break into a password database

Choose how the server stores passwords, then press Breach to play the attacker who stole the database. Each fix reveals the next problem.

attacker@laptop:~$ waiting for a stolen database…
Salt is a random value, different for every user, stored right next to the hash. It is not secret. It kills precomputed rainbow tables and hides that two users chose the same password.
Salt does not slow down an attack on one password, and it cannot make a weak password strong. For that you need a slow hash.

👀 What you should see

Plain text: all 5 exposed at once. SHA-256: 4 of 5 cracked instantly by rainbow table, and alice and carol share a hash. Salted: the table is useless, but weak passwords still fall one user at a time. Slow: every guess is costly. The strong password (eve) is never cracked.

💡 Takeaway

Store passwords with a unique salt plus a slow hash. Salt stops precomputed tables and hides duplicates; a slow hash makes every guess expensive. Neither can rescue a weak password.

Step 2

Speed is the enemy: the attacker's race

For files, a fast hash is good. For passwords, the attacker repeats the hash billions of times, so fast helps them. Time to try every 8-letter lowercase password (268 ≈ 209 billion) on one high-end GPU:

Why memory matters: a GPU has thousands of small cores but little memory each. If one hash needs 64 MB, the GPU cannot run thousands at once.

👀 What you should see

SHA-256 tries every 8-letter lowercase password in seconds. bcrypt and Argon2id barely move and need years.

💡 Takeaway

For passwords, speed helps the attacker. Use a deliberately slow, memory-hard algorithm: Argon2id first, then scrypt or bcrypt. PBKDF2 is the weakest of the four.

Each +1 to the cost roughly doubles the time. You can find the cost that lands in the 250–500 ms zone on this device.

💡 Takeaway

The work factor is tunable. Choose it by measuring on your own server, and raise it as hardware gets faster.

Step 6

Hash chains: Git, blockchain and forensics

Each block stores the hash of the block before it. Edit any block and watch every later block break.

UseHow hashing helps
File integrity monitoringStore baseline digests, compare on a schedule (Tripwire, AIDE)
DeduplicationSame digest means same content
Git commitsCommit ID is a hash of content plus parent
BlockchainEach block contains the previous block's hash
Digital forensicsHash the disk image at seizure; if it still matches at trial, it was not altered

👀 What you should see

Editing one block turns it and every later block red. Restoring the original turns them all green again.

💡 Takeaway

Linking each record to the hash of the previous one makes history tamper-evident. Git, blockchains and forensic evidence all rely on this.
